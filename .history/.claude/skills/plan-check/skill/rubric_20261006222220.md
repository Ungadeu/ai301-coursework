## Checks

| Check | Evidence | Pass condition | Weight |
| --- | --- | --- | --- |
| **diagnosis-grounded** | `plan` (Diagnosis section), `repro_evidence`, `issue` | The plan identifies a specific root cause (not just a surface symptom) that is directly supported by and does not contradict the observed behavior and logs in `repro_evidence`. | `required` |
| **bounded-scope** | `plan` (Scope and Files sections), `issue` | The plan explicitly states both what is IN scope and what is NOT in scope (the boundary), touches only the files necessary for the fix without unrelated refactoring or scope creep, or explicitly states and justifies if it is intentionally scoping down/deferring part of the issue. | `required` |
| **executable-by-a-stranger** | `plan` (Files and Approach sections), `repo_facts` | The plan names the exact existing files/functions to modify (matching the repo structure when filenames are known) and describes a concrete, step-by-step technical approach that another developer could build without guessing. | `required` |
| **test-decisive** | `plan` (Test Plan section), `repro_evidence` | The plan specifies the exact command or automated test to run (re-running the reproduction steps from `repro_evidence`) and explicitly states the concrete expected output after the fix to prove the bug is resolved. | `required` |
| **comment-faithful** | `plan_comment`, `plan`, `comment_thread`, `repo_facts` | The draft `plan_comment` summarizes the diagnosis, approach, and verification plan faithfully without promising changes outside `plan`, directly respects any maintainer constraints or direction in `comment_thread`, and follows all repository policies in `repo_facts` (such as required AI-assistance disclosure or branch/API rules). | `required` |
| **risk-awareness** | `plan` (Risks / Unknowns section) | The plan identifies at least one concrete edge case, caller impact, or regression risk related to the proposed change. | `preferred` |

## Verdict rule

Output `accept` (`ready`) if and only if every `required` check receives a grade of `pass` (`P`). If any `required` check receives `fail` (`F`) or `unclear` (`?`), output `reject` (`hold`). `unclear` (`?`) is always treated as `fail` (`F`) on required checks. `preferred` checks are graded and reported for feedback, but never change the final verdict.
